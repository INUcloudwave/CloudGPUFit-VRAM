# 이미지 분류 중 합성곱 모델의 reserved 예측 방침 (2026-11-17, INUOS)

## 1. 대상

- 대상: 워크로드 유형 "이미지 분류(vision_cls)" 가운데 합성곱(convolution)을 주로 쓰는 모델
  - 현재 조건표에서는 resnet-18, resnet-50, mobilenet-v2
  - vit-large는 첫 단계에서 합성곱을 한 번만 쓰는 트랜스포머라 대상이 아니다.
- LLM(decoder_llm)과 텍스트 인코더-디코더(text_encdec)는 기존 예측 방식 v3를 그대로 쓴다.
  - 일반 조건 100 MB 이내 96.8 %
  - 필요한 GPU 쪽 버퍼는 cuBLAS 작업 공간뿐이고, PyTorch 버전과 GPU 세대로 정해진다.

## 2. 확인된 사실 (근거: `results/reserved_v3/confirm/`, INUGPU 트레이스 13개)

- **할당자 모델은 맞다.**
  - GPU 요청 목록을 그대로 재생하면 11/13 조건이 GPU 실측과 정확히 같다. 나머지 2개도 8 MiB, 2 MiB 차이다.
  - 합성곱 모델 3개(resnet-18·50, mobilenet b128/r512)는 모두 정확히 같다.
- **오차는 요청 목록의 "라이브러리 층"에서 나온다.**
  - 연산 출력(모델 층)은 CPU와 GPU가 같다.
  - 다른 것은 라이브러리가 따로 잡는 버퍼다. CPU는 mkldnn 버퍼, GPU는 cuDNN 작업 공간이다.
  - mobilenet b128/r512에서 CPU 라이브러리 버퍼를 빼면 CPU와 GPU 요청 목록이 4개 실행 모두 완전히 같아진다. 예측도 GPU 실측 6580 MiB와 정확히 같다.
- **cuDNN 작업 공간은 CPU만으로 알 수 없다.**
  - GPU 측정은 `cudnn.benchmark=False`다. 이때 알고리즘은 상황(합성곱 형태, dtype, GPU 세대, cuDNN 버전)에 따라 정해지고, 같은 상황이면 같은 결과가 나온다.
    - 근거: 같은 실행의 warmup·measure 사이에서 같았다. resnet-18과 resnet-50의 같은 형태 첫 합성곱도 둘 다 1280.024 MiB였다.
  - 하지만 선택 함수가 cuDNN 안에 있고 GPU 장치가 있어야 호출된다.
  - 사용자가 쓸 모델·배치·해상도 조합을 미리 다 재 두는 표는 현실적이지 않다.
- **CPU 모델 층 + GPU 라이브러리 층으로 재생하면 3/3 조건이 GPU 실측과 정확히 같다.**
  - resnet-50 6168, resnet-18 2548, mobilenet 6580 MiB
  - GPU 정보 없이(CPU 모델 층 + cuBLAS 작업 공간): mobilenet 6580(정확), resnet-18 2288(−260), resnet-50 4370(−1798). resnet의 남은 차이는 전부 cuDNN 작업 공간이다.
- **오차 크기는 입력 크기에 비례한다.**
  - 100 MB를 넘은 합성곱 모델 조건은 모두 배치 × 해상도²가 큰 경우였다.
  - 배치가 작거나 해상도가 낮으면 대부분 100 MB 이내였다.

## 3. 방침

1. **CPU 라이브러리 버퍼 제거**: GPU 정보가 필요 없다.
   - 연산 출력과 매칭되지 않는 CPU 요청을 뺀다.
   - 층 구분은 연산 종료 시점 표식으로 판정한다(2026-11-17 저녁 수정). CPU malloc의 주소 재사용 때문에 생기던 오분류를 해결했다.
   - 검증 결과: 3/3 조건에서 CPU 모델 층이 GPU 모델 층과 해제 순서까지 같다.
   - mobilenet b128/r512는 이것만으로 GPU 실측과 같다: 6580 = 6580, 기존 v3는 +2072 MiB.
   - 상세: `results/reserved_v3/confirm/hybrid/README_KO.md` §4
2. **cuDNN 작업 공간은 범위로 다룬다.**
   - 하한: 작업 공간 0
   - 상한: 합성곱마다 출력 크기 × k의 임시 버퍼를 출력 직후에 넣고 바로 해제한 것으로 재생한다.
   - k 잠정값 (GPU 트레이스 5개, 측정 구간에서 "출력 직후 할당, 바로 해제"인 요청)

     | 조건 | 최대 배수 | 비고 |
     |---|---|---|
     | resnet-50 b128/r512 | 5.14 | 대부분 2~4배 |
     | resnet-18 b128/r512 | 4.0 | |
     | resnet-50 b8/r224 | 16.8 | 출력이 작아 상대 배수가 크다. 절대값은 18 MiB 이하 |
     | mobilenet b128/r512 | 해당 요청 없음 | |
     | vit-large b128/r224 | 1.78 | |

   - 그래서 상한식은 max(k × 출력, c) 형태가 필요하다. k와 c는 트레이스를 더 받은 뒤 정한다.
   - 모델 3개, 조건 5개에서 본 값이므로 보증된 상한이 아니다.
3. **신뢰도 표시**: 모델에 합성곱 층이 있고 입력이 크면 "예측 신뢰 낮음(범위 보고)"으로 표시한다.
   - 기준값은 검증 후 정한다.
   - 모델 구조와 입력 크기만 보면 되므로 CPU에서 판정할 수 있다.
4. **인스턴스 추천**: 범위의 상한(메모리를 넉넉히 잡는 쪽)으로 판단한다.

## 4. 원리적 한계 (문서에 명시할 것)

- CPU 시뮬레이션만으로는 cuDNN 작업 공간의 정확한 크기와 시점을 알 수 없다. 따라서 합성곱이 많은 모델의 큰 입력에서는 정확한 값 대신 범위만 줄 수 있다.
- 다음 경우에는 상한도 보증되지 않는다.
  - 처음 보는 합성곱 형태
  - 다른 cuDNN·PyTorch 버전
  - `benchmark=True`
  - 용량이 빠듯해 다른 알고리즘으로 넘어가는 경우
